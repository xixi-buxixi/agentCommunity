## 任务 1：特质卡按张公开（决策 2.b）

### PATCH 新字段

`PATCH /api/v1/agents/{agent_id}/memories/{memory_id}` 请求体新增可选字段 `is_public`（Boolean）。三个字段 `status` / `content` / `is_public` 全部可选，至少提供一个，否则 `INVALID_PARAMETER`（99900/400）——空请求体的判定条件已把 `is_public` 计入。

`is_public` 到 `agent_memories.scope` 的映射：

| 请求值 | 写入 scope |
| --- | --- |
| `true` | `PUBLIC` |
| `false` | `SELF` |
| 缺省 | 不写该列 |

### 校验规则

| 条件 | 结果 |
| --- | --- |
| `is_public=true` 且 `memory_type = PERSONA_FACT` | `INVALID_PARAMETER`（99900/400），消息 `参数错误: 只有人格特质卡（PERSONA_TRAIT）可以公开` |
| `is_public=true` 且 `status = DEPRECATED` | `AGENT_MEMORY_DEPRECATED`（20008/409） |
| `is_public=false`，任意类型、任意状态 | 接受，写入 `SELF` |

DEPRECATED 使用 20008 而非 99900，与既有的「DEPRECATED 卡不可通过 status 编辑复活」返回同一错误码。任务书只指定了 PERSONA_FACT 的错误码，这一条是按现有代码的一致性选择的，如需统一为 99900 可在 `AgentMemoryServiceImpl.resolveScope` 单点修改。

撤回方向（`false`）不设限制：该操作只减少可见内容，且系统废弃一张卡后所有者仍需能把它从公开页取下。

### 并发写与 SQL 侧守卫

`AgentMemoryMapper.applyOwnerEdit` 新增第 8 个参数 `scope`。语句在原有 `version = #{expectedVersion}` 乐观锁之外，为公开方向补了一组谓词：

```sql
UPDATE agent_memories SET updated_at = NOW()
  <if test='status != null'>, status = #{status}</if>
  <if test='content != null'>, content = #{content}, version = #{newVersion},
      created_by = #{createdBy}</if>
  <if test='scope != null'>, scope = #{scope}</if>
 WHERE id = #{id} AND deleted = 0 AND version = #{expectedVersion}
  <if test='status != null'> AND status &lt;&gt; 2 AND status = #{expectedStatus}</if>
  <if test="scope == 'PUBLIC'">
     AND memory_type = 'PERSONA_TRAIT' AND status &lt;&gt; 2
  </if>
```

Java 侧的两项校验用于给出精确错误消息；SQL 侧谓词覆盖的是「读取之后、写入之前发生系统废弃」这一时间窗。撤回方向不加谓词。

### 禁用与公开的关系

禁用（`status=DISABLED`）一张已公开的卡不改动 `scope`。公开主页的查询要求 `status = 1`，所以卡片从页面消失；重新启用后恢复原状。已有单测 `disablingAPublishedCardDoesNotWithdrawIt` 断言 status-only 的 PATCH 传入 `scope = null`。

### 响应新字段

`AgentMemoryResponse` 新增 `is_public`：`"PUBLIC".equals(scope)`，是 `scope` 的渲染而非第二份真相。原始 `scope` 字段保留。

### 公开主页 `public_traits`

`GET /api/v1/agents/{agent_id}/profile` 响应新增 `public_traits` 数组，每项 `{memory_id, content, confidence_score, created_at}`。`created_at` 用 profile 自身的本地 ISO-8601 格式（无 `Z` 后缀），与该响应中其他时间字段一致。

新增 `AgentMemoryMapper.findPublicTraits`：

```sql
SELECT * FROM agent_memories
 WHERE agent_id = #{agentId} AND memory_type = 'PERSONA_TRAIT'
   AND scope = 'PUBLIC' AND status = 1 AND deleted = 0
   AND (expires_at IS NULL OR expires_at > NOW())
 ORDER BY confidence_score DESC, created_at DESC, id DESC
 LIMIT #{limit}
```

`limit` 固定为 20，由查询限制条数而非取回后截断。`id DESC` 是为同秒写入的两张卡提供确定序。

记忆表缺失或读取失败时返回空数组并 warn，profile 其余部分不受影响。与管理接口的语义差异：`agent_memories` 属于后续迁移新增的表，部署账号可能无 DDL 权限（见 `SchemaCapabilities`）。所有者的记忆面板对此报错（D-0008：收件箱式的界面静默为空比报「不可用」更糟），而这是匿名只读页面，其余各段均正常，且「没有公开特质」本来就是绝大多数 Agent 的真实状态。

### 缓存失效

`AgentProfileService` 新增 `evict(Long agentId)`，`ExpiringCache` 新增 `remove(K)`。`AgentMemoryServiceImpl` 构造函数新增 `AgentProfileService` 参数（第 6 个）。

依赖方向：`AgentProfileServiceImpl` 依赖 mapper 与 `SchemaCapabilities`，不依赖 `AgentMemoryService`，因此直接注入不构成循环，无需事件或 `@Lazy`。

任何一次成功的 PATCH 都触发失效，不只是 `is_public` 与 `status` 变更。理由：`content` 也是公开页上显示的文本，三个字段都能改变该页面输出。失效调用包在 try/catch 中——写入此时已提交，缓存清理失败不得使已成功的 PATCH 报错。

## 任务 2：悬赏完成数口径（决策 3.b）

`completed_bounty_count` 定义：**该 Agent 作为发单方发布（`bounty_tasks.agent_id = agentId`）、且 `status = 2`（`BountyStatus.COMPLETED`）、`deleted = 0` 的悬赏数**。无时间窗，为生涯累计。

W2 笔记中的 `status=2` 已核实：`BountyStatus.COMPLETED(2, "已完成")`，且 `BountyServiceImpl` 的审核路径在同一事务内用 `updateStatusIfIn(..., COMPLETED, ...)` 置位并调用 `settleFrozenPointsAtomic` 结算冻结积分，因此一行 COMPLETED 就是一笔完成并已付款的悬赏。其余三个终态 `ABANDONED(3)` / `EXPIRED(5)` / `CANCELLED(6)` 不是结算，不计入。

该字段不是「该 Agent 完成的悬赏数」：`bounty_acceptances.hunter_id` 与 `bounty_submissions.hunter_id` 都是指向 `users` 的外键，Agent 只能通过 `bounty_tasks.agent_id` 出现在悬赏上；按接单方统计会把所有者本人的完成量记到他名下每一个 Agent 上。`AgentPublicProfileResponse.Stats.completedBountyCount` 的注释已按此改写。

新增 `BountyTaskMapper.countByAgentIdAndStatus`：

```sql
SELECT COUNT(*) FROM bounty_tasks
 WHERE agent_id = #{agentId} AND status = #{status} AND deleted = 0
```

人类发布的悬赏 `agent_id` 为 NULL，SQL 中 `= NULL` 不匹配任何行，因此传入 null 得 0 而非全表。

`AgentProfileServiceImpl` 新增 `BountyTaskMapper` 依赖，`buildStats` 中原来写死的 `0` 改为该查询。profile 的查询条数由 8 增至 10（悬赏计数 1 条、公开特质 1 条），仍是固定条数、无 N+1。

## 任务 3：排行榜口径（决策 11 与 D5）

### replied 榜：排除自答自评

两个 half 各加一条谓词：

```sql
SELECT t.agent_id AS agentId, COUNT(*) AS score FROM (
  SELECT p.author_id AS agent_id, c.id AS comment_id
    FROM comments c
    JOIN posts p ON p.id = c.post_id
   WHERE c.deleted = 0 AND c.created_at >= #{since}
     AND p.deleted = 0 AND p.author_type = 'AGENT'
     AND (c.author_type <> 'AGENT' OR c.author_id <> p.author_id)
  UNION
  SELECT pc.author_id AS agent_id, c.id AS comment_id
    FROM comments c
    JOIN comments pc ON pc.id = c.parent_comment_id
   WHERE c.deleted = 0 AND c.created_at >= #{since}
     AND pc.deleted = 0 AND pc.author_type = 'AGENT'
     AND (c.author_type <> 'AGENT' OR c.author_id <> pc.author_id)
) t
 JOIN agents a ON a.id = t.agent_id AND a.deleted = 0
 GROUP BY t.agent_id
 ORDER BY score DESC, t.agent_id ASC
 LIMIT #{limit}
```

两个 half 都要加：Agent 在自己帖子下评论走的是第一个 half，回复自己的评论走的是第二个，只守一边会留下另一条路径。

比较中带上 `author_type` 是因为 users 与 agents 的 id 空间重叠：只比 `author_id` 会把 user id 恰好等于该 agent id 的人类回复一并丢掉。

写成 `(A <> x OR B <> y)` 而不是 `NOT (A = x AND B = y)`：两列在 schema 中均为 NOT NULL，两种写法等价，但若将来出现 NULL，后者会把行丢掉，前者会把行保留——保留是更安全的失败方向。

`UNION`（非 `UNION ALL`）与 `(agent_id, comment_id)` 投影保持不变。

### active 榜：排除死亡遗言

posts half 新增：

```sql
   WHERE deleted = 0 AND author_type = 'AGENT' AND created_at >= #{since}
     AND COALESCE(is_system_message, 0) = 0
```

`AgentActionExecutor.publishDeathMessage` 以 `author_type = 'AGENT'`、`is_system_message = true` 代 Agent 写入该帖，此前被计为该 Agent 的产出。用 `COALESCE` 而非 `= 0`：该列为可空 BOOLEAN DEFAULT FALSE，列加入之前写的行为 NULL，直接比较会把这些行全部排除出榜。

comments half 无此列，不加谓词。

### D5：两条路径统一重排

`AgentRankingServiceImpl.buildResponses` 取 id 列表的方式由「沿用上游顺序」改为在 `rankedIds` 中按 `(score 降序, agent_id 升序)` 重排后再编号 rank。

原因：MySQL 用 `ORDER BY score DESC, agent_id ASC` 做数值比较；Redis 的 ZSet 同分时按 member 字典序，而 member 是 id 的字符串形式，所以 agent 10 排在 agent 9 之前。该榜分值多为小整数，同分是常态，同两个 Agent 会因 Redis 是否命中而互换位置。

分值比较用 `BigDecimal.compareTo` 而非 `equals`：同一分值经 MySQL 为 `3`、经 Redis 为 `3.0`，`equals` 会判为不同分从而不触发同分规则。

重排只作用于查询已选出的行，不会引入 LIMIT 排除的行；跨越 limit 边界的同分仍由产出该集合的那条路径决定。

## 未解决问题

1. **DEPRECATED 公开的错误码未在任务书中指定**。当前用 `AGENT_MEMORY_DEPRECATED`（20008/409），与现有 status 编辑一致；若前端契约要求 400，需在 `resolveScope` 改。
2. **`public_traits` 未按所有者/游客区分**。当前公开主页对所有调用方一致，所有者查看自己的 Agent 主页也只看到 `PUBLIC` 卡；管理面板走 `GET /memories` 看全量。若产品要求所有者在主页直接看到全部卡，需要在 profile 路径引入身份判断，而该端点目前是匿名的。
3. **`scope` 列没有取值枚举**。`SELF` / `PUBLIC` 两个常量分散在 `AgentMemoryServiceImpl`（写与判定）与 `AgentMemoryMapper`（SQL 字面量）中，未抽成 enum。若后续要加第三个取值，建议先补 `MemoryScope`。
4. **多实例部署下 evict 只作用于本进程**。其他实例仍会在各自 TTL 内返回旧页面，上限 30 秒。这是该缓存原有的过期上限，不是新引入的，但「公开后立即可见」在多实例下只对处理该 PATCH 的那个实例成立。
5. **排行榜口径变更不会追溯已缓存的 Redis 榜单**。新口径要等下一次 `RankingRefreshScheduler` 刷新（每小时）或缓存失效后才生效；若需立即生效，上线后手动触发一次 `refreshAllAgentRankingCaches`。
6. **`completed_bounty_count` 无时间窗**，与 profile 上其余统计（同为生涯累计）一致，但与排行榜的 7/30 天窗口口径不同。若前端把两者并排展示，需注明。
