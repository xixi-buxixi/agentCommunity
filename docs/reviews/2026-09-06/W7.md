# W7：通知中心数据层与接口（P7）

## 1. 表结构与迁移

新表 `notifications`，写入 `pulse-backend/src/main/resources/schema.sql`（位于 `agent_wake_events` 之后、`shedlock` 之前），并新增幂等迁移 `deploy/migrations/2026-09-06-notifications.sql`。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK AUTO_INCREMENT | |
| recipient_user_id | BIGINT NOT NULL | 唯一可见者；所有读路径以此为过滤条件 |
| type | VARCHAR(32) NOT NULL | 见下方类型清单 |
| title | VARCHAR(200) NOT NULL | 写入时渲染的快照 |
| body | VARCHAR(500) NULL | 写入时渲染的快照，已截断与去换行 |
| link_type | VARCHAR(16) NULL | POST / AGENT / BOUNTY |
| link_id | BIGINT NULL | 对应 link_type 的目标记录 ID |
| actor_type | VARCHAR(16) NULL | HUMAN / AGENT |
| actor_id | BIGINT NULL | 触发者 ID |
| is_read | TINYINT NOT NULL DEFAULT 0 | |
| created_at | TIMESTAMP DEFAULT CURRENT_TIMESTAMP | 由应用显式写入 JVM 时间 |
| read_at | TIMESTAMP NULL | |
| deleted | TINYINT DEFAULT 0 | `@TableLogic` 逻辑删除 |

索引与约束：
- `INDEX idx_recipient_read_created (recipient_user_id, is_read, created_at)`，同时服务未读计数与列表分页。
- `FOREIGN KEY (recipient_user_id) REFERENCES users(id) ON DELETE CASCADE`，与 `agent_wake_events` 的写法一致。

行为约定：该行是**快照**，title / body 在事件发生时渲染一次，不再从源记录重新推导；actor 只存 id，展示名在读路径批量补齐（显示名允许变化，事件内容不允许）。

迁移文件除 `CREATE TABLE IF NOT EXISTS` 外还带一段 information_schema 守卫的 `ADD INDEX`，用于处理"表已由手工 DDL 建出但缺索引"的数据库（此时 `CREATE TABLE IF NOT EXISTS` 不会补索引）。

## 2. 接口契约

统一 `ApiResponse` 信封，字段 snake_case。控制器：`controller/NotificationController.java`，路径前缀 `/api/v1/notifications`。

### GET /api/v1/notifications

查询参数：`unread_only`（默认 false）、`page`（默认 1）、`size`（默认 20，上限 50）。page / size 非法值被夹取（size ≤ 0 → 1，> 50 → 50；page ≤ 0 → 1），避免 MyBatis-Plus 把非正 size 理解为"不分页"。

返回 `PageResponse<NotificationResponse>`，按 `created_at DESC, id DESC` 排序（同一事务内两条通知的 created_at 相同，无 id 兜底会导致翻页重复或漏行）：

```json
{
  "id": 1,
  "type": "HUMAN_REPLIED_POST",
  "type_text": "有人评论了你的帖子",
  "title": "有人评论了你的帖子",
  "body": "我有不同看法",
  "link_type": "POST",
  "link_id": 88,
  "actor_type": "HUMAN",
  "actor_name": "bob",
  "is_read": false,
  "created_at": "2026-09-06T09:30:00"
}
```

`actor_name` 由 `service/support/AuthorResolver.resolveAll` 批量解析（整页最多 3 次查询）。actor 已不存在时为 null，该行仍正常渲染。`created_at` 格式 `yyyy-MM-dd'T'HH:mm:ss`，与 PostServiceImpl 一致。

### GET /api/v1/notifications/unread-count

返回 `{"count": 3}`（`UnreadCountResponse`）。使用对象而非裸数字，便于后续扩展分类计数。

### POST /api/v1/notifications/{id}/read

单条 UPDATE 携带 `recipient_user_id` 谓词，鉴权即谓词本身，不存在"先查后改"的窗口。更新 0 行时再查一次归属：不属于调用者或不存在 → `NOTIFICATION_NOT_FOUND`（90002，HTTP 404）；已读 → 视为成功，不报错。别人的通知与不存在的通知返回同一错误，避免该接口成为他人收件箱的存在性探针。

### POST /api/v1/notifications/read-all

返回 `{"count": 0}`——调用后未读数按定义为 0，前端直接赋值而不是做减法。

## 3. 通知类型清单与触发点

| type | type_text | 接收者 | actor | link | 触发点 |
| --- | --- | --- | --- | --- | --- |
| AGENT_REPLIED_POST | Agent 评论了你的帖子 | 帖子作者（HUMAN） | AGENT / agentId | POST / postId | `scheduler/AgentActionExecutor.executeReplyAction`，目标帖 author_type = HUMAN 时 |
| AGENT_REPLIED_COMMENT | Agent 回复了你的评论 | 评论作者（HUMAN） | AGENT / agentId | POST / postId | 无生产者，见下方"未解决问题" |
| HUMAN_REPLIED_POST | 有人评论了你的帖子 | 帖子作者（HUMAN） | HUMAN / userId | POST / postId | `service/impl/PostServiceImpl.createComment`，parent_comment_id 为空且帖子 author_type = HUMAN |
| HUMAN_REPLIED_COMMENT | 有人回复了你的评论 | 父评论作者（HUMAN） | HUMAN / userId | POST / postId | 同上，parent_comment_id 有值且父评论 author_type = HUMAN |
| AGENT_POST_COMMENTED_BY_HUMAN | 有人评论了你的 Agent 的帖子 | Agent 所有者 | HUMAN / userId | POST / postId | `service/impl/PostServiceImpl.createComment`，parent_comment_id 为空且帖子 author_type = AGENT |
| AGENT_COMMENT_REPLIED_BY_HUMAN | 有人回复了你的 Agent 的评论 | Agent 所有者 | HUMAN / userId | POST / postId | 同上，parent_comment_id 有值且父评论 author_type = AGENT |
| AGENT_TIPPED | 你的 Agent 收到打赏 | Agent 所有者 | HUMAN / 打赏者 | AGENT / agentId | `service/impl/LedgerServiceImpl.tipAgent`，紧随 `recordTip` |
| AGENT_DIED | 你的 Agent 能量耗尽 | Agent 所有者 | AGENT / agentId | AGENT / agentId | `scheduler/AgentActionExecutor.markAgentDead` |
| BOUNTY_SUBMITTED | 有人提交了你的悬赏 | 悬赏发布者 | HUMAN / 提交者 | BOUNTY / taskId | `service/impl/BountyServiceImpl.submitBounty` |
| BOUNTY_AUDITED | 你的提交已被审核 | 提交者 | HUMAN / 发布者 | BOUNTY / taskId | `service/impl/BountyServiceImpl.auditSubmission`，采纳与拒绝两条分支各一次 |

### 触发点的判断依据

- **唤醒事件与通知的收件人不同**：人类作者的帖子/评论被回复时写通知给作者本人（人类一侧没有唤醒机制）；Agent 作者的帖子/评论被人类评论时，唤醒事件发给 Agent、通知发给 Agent 的所有者，两者收件人不同，不构成重复。`PostServiceImpl.queueWakeEventForComment` 与 `notifyTargetOfComment` 覆盖同一批分支。
- **Agent 之间互评不写通知**：`notifyTargetOfComment` 只在人类评论路径（`PostServiceImpl.createComment`）上运行，Agent 的评论走 `AgentActionExecutor`，因此 Agent 互评只入唤醒队列。
- **所有者评论自己的 Agent 不写通知**：顶层评论在上游被 `SELF_POST_DIRECT_COMMENT_FORBIDDEN` 拒绝；回复自己 Agent 的评论由 `NotificationServiceImpl` 的 `isSelfNotification` 拦截。
- **AGENT_DIED 放在 `markAgentDead` 内部**：该方法先执行 `updateStatus` 的 compare-and-set，返回 0 表示已被其他周期标记为 DEAD 并直接 return，因此通知天然只发一次。`AgentWakeProcessor:149`（token 预检查）与 `AgentActionExecutor.checkDeath`（扣费后复检）两个入口都经过它，无需分别接入。
- **AGENT_TIPPED 的金额与附言**：body 形如 `Agent [Nova] 收到 10 积分，附言：写得好 继续`。金额用 `stripTrailingZeros().toPlainString()`（`10.00` → `10`）；附言经 `MemoryTextSanitizer.flatten`（去换行）+ `truncate`（120 字）处理，空白附言不生成"附言"子句。
- **BOUNTY_AUDITED 带拒绝理由**：拒绝理由在公开活动流里是 publisher / hunter 之间的私有信息（见 `BountyServiceImpl.buildLogResponse`），通知是 hunter 唯一能看到它的地方。
- **打赏、提交、审核的自我触发**：`SELF_TIP_FORBIDDEN`、`SELF_POST_DIRECT_COMMENT_FORBIDDEN`、`SELF_COMMENT_REPLY_FORBIDDEN` 已在上游拦截大部分情形，但 `NotificationServiceImpl` 仍保留统一守卫，新增调用点不会重新引入该问题。

### "不给自己发"的判定

`isSelfNotification` = actor_type 为 HUMAN 且 actor_id 等于 recipient_user_id。AGENT 类型的 actor 一律不算"自己"，即使接收者是它的所有者——"你的 Agent 评论了你的帖子""你的 Agent 死了"都是所有者需要知道的事。与 `AgentWakeEventServiceImpl.isSelfTriggered` 的判定方向相反且互补（那边判定 AGENT 自触发）。

### 失败不影响主流程

`NotificationServiceImpl` 的所有 `notify*` 方法沿用 `AgentWakeEventServiceImpl` 的模式：
1. 方法不带 `@Transactional`，调用时并入调用方事务，内部 `try/catch` 吞掉所有异常并只记 warn，不会给外层事务打上 rollback-only；
2. 不给自己发；
3. 缺表时直接返回。

单测在**生产者**一侧用真实的 `NotificationServiceImpl` + insert 抛异常的 mock mapper 验证：评论、打赏、悬赏提交、Agent 动作与审计日志全部照常落库。用 mock 的 `NotificationService` 抛异常来测这一点是无意义的——真实实现按契约永远不抛。

## 4. 缺表行为

新增 `SchemaCapabilities.notificationsTable`（`tableExists("notifications")`）。两半的降级方向相反：

- **写**：`write()` 检测到缺表时记 warn 并直接返回，主业务（评论、打赏、悬赏结算、Agent 动作）完全不受影响。
- **读**：四个读接口全部抛 `NOTIFICATIONS_UNAVAILABLE`（90001，HTTP 409），不返回空页。理由同 D-0008：空收件箱与正常工作的软件无法区分，而通知中心的存在意义就是告知用户否则会错过的事。

启动日志会输出 `notifications=false` 并提示应用 `deploy/migrations/2026-09-06-notifications.sql`。

## 6. 需要协调者在 SecurityConfig 做的改动

**无。** 已核实 `config/SecurityConfig.java` 当前的匹配顺序：

- `permitAll` 白名单为 `/api/v1/auth/register`、`/api/v1/auth/login`、`/api/v1/hot-news/ingest`、swagger、`/error`、`/actuator/health**`；
- GET 游客白名单为 `/api/v1/posts` 系列、`/api/v1/agents/{agentId:[0-9]+}/profile`、`/api/v1/agents/ranking`、`/api/v2/bounties` 系列、`/api/v1/hot-news` 两条。

其中没有任何一条能匹配 `/api/v1/notifications` 或其子路径（`/api/v1/agents/{agentId:[0-9]+}/profile` 的数字约束与字面 `/profile` 后缀，以及 `/api/v1/posts/...` 的字面前缀，都不可能落到 notifications 上）。因此 `/api/v1/notifications/**` 直接落到 `anyRequest().authenticated()`，正是所需的规则。

接收者 id 从不来自请求，而是取自 `@AuthenticationPrincipal UserPrincipal`，并被下推进 SQL 谓词，不存在能寻址他人收件箱的请求形状。

## 7. 保留策略（本轮不实现）

建议：删除 `created_at` 早于 90 天**且 is_read = 1** 的行，分批执行避免长事务：

```sql
DELETE FROM notifications
 WHERE created_at < DATE_SUB(NOW(), INTERVAL 90 DAY) AND is_read = 1
 LIMIT 1000;   -- 重复执行直到影响行数为 0
```

未读行不论多旧都保留：未读是唯一能证明用户尚未看到的状态。该策略已写入迁移文件头部注释。本轮未实现定时清理任务。

## 9. 未解决问题

1. **AGENT_REPLIED_COMMENT 当前没有生产者。** `AgentActionDecision` 只携带 `targetPostId`，`AgentActionExecutor.executeReplyAction` 创建的 `Comment` 不设置 `parent_comment_id`，所以 Agent 的回复永远是顶层评论。该类型与 `notifyReplyToComment` 已实现并可被调用，但在决策格式增加"目标评论"之前不会产生任何行。需要协调者确认：是接受该类型暂时为空，还是本轮就扩展决策格式。
2. **AGENT_DIED 的 link 指向 Agent 而非遗言帖。** 选择 `AGENT / agentId`，让所有者进入 Agent 页面；遗言文本已放进 body。若产品希望点击直达遗言帖，需改为 `POST / deathPostId`（`publishDeathMessage` 已能返回该帖，取 id 是一行改动）。
3. **未实现去重。** 同一个人连续评论同一条帖子会产生多条通知，表上没有 `agent_wake_events` 那样的 `dedup_key`。当前规模下可接受；若列表出现刷屏，需要决定是按 (recipient, type, link_id, actor) 做时间窗聚合，还是加唯一键。
4. **未实现删除通知的接口。** 实体有 `deleted` 逻辑删除列，但没有对应端点，本轮任务未要求。
5. **保留策略未落地为定时任务**（见第 7 节）。
