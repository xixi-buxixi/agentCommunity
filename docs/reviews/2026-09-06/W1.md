## 错误码处理

### 记忆相关（`describeMemoryError`，`src/utils/memory.js`）

| 来源 | 前端文案 |
| --- | --- |
| 20002 | Agent 不存在 |
| 20003 | 无权查看该 Agent 的记忆 |
| 20007 | 记忆不存在或不属于该 Agent |
| 20008 | 已废弃的记忆不可恢复 |
| 99900 | 请求内容无效：至少要修改状态或内容，且状态只能为生效中/已禁用 |
| 99904 | 该记忆已被其他操作更新，请刷新后重试 |
| HTTP status >= 500 | 当前部署未启用记忆表（agent_memories），请先执行记忆表迁移 |
| 其他 | 后端 message，缺失时为 `MEMORY_REQUEST_FAILED` |

判定顺序为先业务码后 HTTP status，因此 500 之外的失败不会被误判为缺表。

20008 还有一层前端拦截：`canReactivate` 只对 DISABLED 返回 true，DEPRECATED 卡片的 RESTORE 按钮为 disabled 并带 title 提示，正常路径下不会把该请求发出去；`reactivateMemory` 内另有一次判定作为兜底。

列表加载失败时面板整体显示错误与 `[RETRY]`；单条操作失败时错误显示在该卡片下方，不影响其他卡片。

## request.js 的改动说明

改动只有一处，在响应拦截器的 `onFulfilled` 分支（HTTP 2xx 但 `code` 非成功值）：

原来 reject `new Error(message)`，Error 上没有 `code` 与 `status`；transport 失败分支（`onRejected`）此前就已经在 Error 上写了 `status` / `code` / `cause`。这个不对称使得调用方无法在不区分传输层形态的前提下按业务码分支。

改后该分支同样 reject 一个带 `status`（取 `response.status`，业务错误时为 200）与 `code`（`typeof code === 'number' ? code : null`）的 Error。

未改变的部分：
- 成功路径仍然 resolve `{ data, message }`；
- `SESSION_INVALID_CODES` 的 `clearAuthAndRedirect()` 调用位置与时机不变；
- `console.error` 的终端风格日志不变；
- Error 的 `message` 仍是后端 message，因此所有只读 `error.message` 的既有调用方行为不变；
- transport 失败分支未改动。

对 `describeMemoryError` 的影响：业务错误分支产生的 Error 其 `status` 为 200，不会触碰 `status >= 500` 的缺表分支；真正的 500 走 transport 分支，`status` 为 500。

## 契约不一致与需要注意的点

1. **类型文案两处不一致。** `docs/contracts/overview.md` 与任务说明把 PERSONA_FACT / PERSONA_TRAIT 描述为「结构化事实」「特质」，而 `com.pulse.enums.MemoryType` 的 text 是「行为事实」「人格特质」，`memory_type_text` 返回后者。前端筛选项已统一采用枚举的措辞，`typeLabel` 优先使用后端返回的 `memory_type_text`。

2. **作息字段无法清空。** `AgentUpdateRequest` 的三个字段是「不传即保留」语义，没有表达「清除已存值」的方式。前端下拉里的「未设置」只能作为初始状态（legacy 部署读回 null），把已设置的下拉改回「未设置」不会提交任何字段，也就无法把值删掉。若后续需要清空能力，需要后端补一个显式的语义。

3. **20009 的触发条件比文档窄。** 契约写「On a database without the wake columns … a wake-settings update fails with 20009」。因此只在实际带上了 wake 字段时才可能收到 20009；前端只提交改动过的字段，正好符合这一点，但也意味着用户不改作息时无法从更新接口得知当前部署是否启用了唤醒队列。前端的替代信号是详情/列表里三个字段是否为 null（Monitor 与卡片显示 `N/A`）。

4. **记忆列表分页上限。** 契约说 size 被静默 clamp 到 1-50。前端固定用 `size=10`，并在 `buildMemoryQuery` 内本地 clamp 到 50，二者不冲突。

5. **`AgentMemoryResponse` 有契约文档未提及的字段**：`evidence`、`scope`、`importance_score`。面板目前只展示 `content` / `confidence_score` / `source_type`+`source_id` / `created_at` / `expires_at` / `status` / `version`，未展示这三个。

6. **时间字符串格式未在契约中固定。** `created_at` / `expires_at` / `next_wake_at` 在 DTO 里都是 String。`parseBackendTime` 同时接受 `2026-07-28T09:00:00` 与 `2026-07-28 09:00:00`，后者直接 `new Date()` 在 Safari 上会得到 Invalid Date。

7. **特质时间线的分组范围限于当前页。** 时间线视图复用同一个分页接口（`memory_type=PERSONA_TRAIT`），分组在当前页的数据上进行，跨页的同一天会分别成组。分页控件在该视图下同样可用。

8. **Monitor.vue 原有的死字段一并修正。** 该页 `INSTANCE_CONFIG` 区块此前也在读 `next_wakeup_at` 与 `daily_bounty_count`，与 AgentRackCard.vue 是同一类问题，本次一并改为真实字段。
